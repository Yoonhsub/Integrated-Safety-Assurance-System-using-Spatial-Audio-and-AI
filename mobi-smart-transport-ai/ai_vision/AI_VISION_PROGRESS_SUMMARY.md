# AI Vision 진행 현황 및 팀 공유 자료

## 한 문장 요약

카메라 화면에서 버스·버스 문·방치 전동 킥보드·기둥·나무 줄기·버스 정류장을 함께 찾는
하나의 Android용 TFLite 모델을 만들었다. 내부 테스트까지 끝났고, 이제 개발 일정의
Android 실기기·현장 검증 단계에서 실제 정류장 장면의 놓침과 오탐을 확인해야 한다.

## 완료한 작업

| 구분 | 완료 내용 | 의미 |
| --- | --- | --- |
| Android AI 기준선 | COCO 버스 모델을 Android용 `.tflite`로 변환 | 서버 없이 휴대폰 안에서 버스 탐지 가능 |
| 모델 입출력 규칙 | `640×640 RGB float32` 입력, `[1,84,8400]` 출력 해석 확정 | 앱에서 같은 규칙으로 구현 가능 |
| 버스 위치 판단 | `LEFT / CENTER / RIGHT` | 어느 방향에 버스가 있는지 전달 |
| 상대 거리 판단 | `FAR / MEDIUM / NEAR` | 화면 속 버스 크기를 기준으로 가까움 판단 |
| 움직임 판단 | `APPROACHING / STABLE / RECEDING` | 이전 프레임과 비교해 가까워지는 흐름 판단 |
| 실제 모델 검증 | 공개 버스 이미지·영상으로 TFLite 실행 | 영상에서 `CENTER/MEDIUM` → `LEFT/NEAR/APPROACHING` 전환 확인 |
| 앱 연동 문서 | Android TFLite 인계서 작성 | 카메라·권한·모델 실행을 앱에서 구현할 기준 제공 |
| 데이터셋 준비 | 라벨링 기준, 개인정보 처리, 자동 검증기 작성 | 잘못된 라벨·파일 누락을 학습 전에 검사 |
| 버스 문 모델 학습 | 공개 데이터로 20회 학습 완료 | `bus`·`bus_door` 구분 모델 확보 |
| 버스 문 안내 후보 검증 | 실제 테스트 이미지에서 `bus`·`bus_door` 후보 생성 확인 | Android 전 AI Vision 연결 검증 완료 |
| 버스 문 Android 모델 | 버스 문 가중치를 float32 TFLite로 변환·실행 검증 | 앱에서 바로 사용할 모델과 입출력 규격 확보 |
| Context·Audio 연동 준비 | 실제 결과 형식의 고정 예시와 자동 검사 추가 | 음성 정책 담당자가 공용 계약 변경 전 연동 흐름을 검토 가능 |
| 통합 현장 검증 모델 | 버스·버스 문·전동 킥보드·기둥·나무 줄기·버스 정류장을 한 모델로 20회 학습·TFLite 변환 | Android에서 모델 하나만 실행해 여섯 대상을 함께 현장 검증 가능 |

## 공개 버스 문 데이터셋 처리 결과

| 항목 | 결과 |
| --- | ---: |
| 전체 이미지 | 1,884장 |
| 학습 / 검증 / 테스트 | 1,507 / 188 / 189장 |
| 유지한 `bus`·`bus_door` 라벨 | 4,459개 |
| 제거한 `Number` 라벨 | 576개 |
| 데이터셋 형식 검사 | 오류 0개 |

원본의 `Front_door`, `Rear_door`는 프로젝트의 단일 `bus_door` 클래스로 합쳤고,
`Number`는 안내 기능과 무관하므로 제외했다.

## 버스 문 모델 학습 완료

공개 데이터 1,884장으로 `bus`와 `bus_door`를 20회 학습했다. 최종 검증에서 전체
`mAP50`은 `0.993`, 버스 문 클래스의 `mAP50`은 `0.993`이었다. 학습 가중치와 해시,
재현 방법은 [버스 문 모델 산출물](BUS_DOOR_MODEL_RELEASE.md)에 기록했다.

## 현재 통합 모델 평가

현재 Android 현장 검증에 쓸 파일은
`ai_vision/models/yolo11n_unified_bus_obstacle_stop_v2_float32.tflite` 하나다. 버스 문,
전동 킥보드, 기둥·나무의 기존 개별 모델은 비교용 기준선으로만 보관한다.

기존 데이터와 추가 국내 인도보행 데이터의 학습/검증/테스트 구분을 유지해 합친 결과, 전체 29,885장 중
20,839장으로 학습하고 4,503장으로 검증했으며, 4,543장은 학습에 사용하지 않은 테스트로
남겼다. 테스트 결과는 아래와 같다.

| 클래스 | Precision | Recall | mAP50 | mAP50-95 |
| --- | ---: | ---: | ---: | ---: |
| 전체 | 0.844 | 0.798 | 0.849 | 0.647 |
| `bus` | 0.993 | 0.995 | 0.995 | 0.955 |
| `bus_door` | 0.988 | 0.976 | 0.992 | 0.818 |
| `parked_pm` | 0.853 | 0.832 | 0.881 | 0.683 |
| `pole` | 0.781 | 0.812 | 0.871 | 0.612 |
| `tree_trunk` | 0.829 | 0.695 | 0.820 | 0.499 |
| `bus_stop` | 0.622 | 0.481 | 0.536 | 0.313 |

이 수치는 원본 데이터 내부 테스트 결과다. `bus_stop`은 기존 모델의 mAP50 0.441보다
0.536으로 개선됐지만, 쉘터·벤치가 있는 정류장 장면 중심으로 학습됐다. 따라서 현재는 정류장 후보를 화면에 표시하고
기록하는 용도로만 쓰며, 표지판만 있는 정류장과 다양한 국내 정류장 장면을 추가해
fine-tuning해야 한다. 나무 줄기도 놓침 가능성이 남아 있다.
상세 사용법은 [통합 모델 현장 검증 인계서](UNIFIED_MODEL_FIELD_TEST_HANDOFF.md)를 따른다.

## 개별 모델별 점수 이력

아래 점수는 모두 같은 시험에서 나온 값이 아니다. 버스·버스 문과 킥보드는 각각의 공개
데이터 내부 평가이고, 기둥·나무는 국내 AI Hub 보행 데이터 평가이다. 따라서 숫자만으로
서로의 실제 현장 성능을 단정하지 않으며, 모든 장애물 모델은 실제 정류장·보도 카메라
검증이 남아 있다.

| 대상 | 평가 데이터 / 조건 | Precision | Recall | mAP50 | mAP50-95 | 현재 판단 |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| `bus` | 공개 버스 문 데이터 검증 | 1.000 | 0.992 | 0.995 | 0.965 | TFLite 변환·PC 추론 확인 완료 |
| `bus_door` | 공개 버스 문 데이터 검증 | 0.972 | 0.993 | 0.993 | 0.815 | TFLite 변환·PC 추론 확인 완료 |
| `parked_pm` (전동 킥보드) | 초기 공개 데이터 파일럿, 131장 / 502개 객체 | 0.943 | 0.662 | 0.864 | 0.629 | TFLite 변환 완료, 국내 정류장·보도 현장 검증 전 |
| `pole` | 국내 보행 데이터 검증 | 0.682 | 0.798 | 0.792 | 0.512 | TFLite 변환 완료, 현장 검증·fine-tuning 전 |
| `tree_trunk` | 국내 보행 데이터 검증 | 0.771 | 0.721 | 0.810 | 0.478 | TFLite 변환 완료, 현장 검증·fine-tuning 전 |

기둥·나무 두 클래스를 함께 평가한 독립 테스트(학습에 사용하지 않은 2,193장)에서는
Precision `0.723`, Recall `0.717`, mAP50 `0.766`, mAP50-95 `0.445`였다. 이 수치는
현장 테스트가 아니라 AI Hub 내부 시퀀스 분리 테스트 결과다.

## 장애물 데이터 실험 결과

정류장 사진과 공개 데이터를 이용해 `parked_pm`, `sidewalk_pole`, `tree_trunk`를
시험했다. 공개 데이터 내부 성능과 달리 국내 정류장 이미지 성능이 충분하지 않았다.
특히 기둥 모델은 국내 테스트에서 거의 전이되지 않았고, 나무 줄기 모델도 재현율이
낮았다. 따라서 기둥·나무는 실제 안내 대상에서 보류하고, 국내 정류장 데이터를
추가로 확보한 뒤 재개한다.

이후 AI Hub 국내 도로 이미지 708쌍으로 `Column & Tree`를 통합한
`vertical_obstacle` 모델도 별도 학습했다. 미사용 국내 테스트 106장에서 mAP50은
0.299, 재현율은 0.311로 아직 낮았다. 특히 원거리의 가는 세로 객체를 놓치거나 박스가
불안정해, 이 모델 역시 실제 안내에는 추가하지 않고 보류한다.

원거리의 매우 가는 bbox를 제외하고 가까운 객체 중심으로 재학습한 2차 모델은 같은
테스트에서 mAP50 0.452, 재현율 0.431까지 개선됐다. 하지만 안전 안내에 필요한 수준에는
부족하고 차량 주행 시점 데이터라는 한계가 있으므로, 이 역시 연구용 결과로만 보관한다.

## 국내 보행 데이터 기반 기둥·나무 모델 학습 완료

차량 시점 데이터의 한계를 보완하기 위해 AI Hub 인도보행 데이터의 `Bbox_10_new`
묶음을 사용해 새 학습 데이터를 만들었다. 이 데이터는 실제 사진이지만 보행 영상을
프레임으로 나눈 것이므로, 같은 장소의 비슷한 장면이 학습과 평가에 함께 들어가지 않도록
**XML 촬영 시퀀스 단위**로 분할했다.

| 항목 | 결과 |
| --- | ---: |
| 전체 이미지 | 11,781장 |
| `pole` 박스 | 12,458개 |
| `tree_trunk` 박스 | 14,736개 |
| 전체 대상 박스 | 27,194개 |
| 학습 / 검증 / 테스트 이미지 | 7,794 / 1,794 / 2,193장 |
| 학습 모델 | YOLO11n 사전학습 모델, 20회 학습 |

XML의 `pole`과 `tree_trunk`만 YOLO 형식으로 변환했으며, 그 외 객체는 이 모델의
대상이 아니다. `scooter` 라벨은 이 묶음에서 24개뿐이어서 포함하지 않았다. 킥보드는
별도 데이터로 다룬다.

20회 학습 후, 검증 분할에서 가장 좋았던 가중치(`best.pt`)를 선택했다. 검증 분할과
학습에 사용하지 않은 테스트 분할의 결과는 다음과 같다.

| 평가 구간 | Precision | Recall | mAP50 | mAP50-95 |
| --- | ---: | ---: | ---: | ---: |
| 검증 (1,794장) | 0.727 | 0.759 | 0.802 | 0.495 |
| 독립 테스트 (2,193장) | 0.723 | 0.717 | 0.766 | 0.445 |

검증과 독립 테스트의 차이가 크지 않아 AI Hub 국내 보행 장면 안에서는 일정 수준의
일반화가 확인됐다. 하지만 두 분할 모두 같은 데이터 출처이므로, 실제 정류장·보도·휴대폰
카메라 환경에 곧바로 적용 가능한지까지 의미하지는 않는다. 현장 검증과 fine-tuning 계획은
[기둥·나무 모델 결과 및 보완 계획](SIDEWALK_POLE_TREE_MODEL_RELEASE.md)에 정리했다.

## 남은 개발 일정

1. Android 앱에 통합 TFLite 모델 하나를 넣고 후면 카메라 프레임 연결
2. Android 실기기에서 여섯 클래스의 검출·놓침·오탐·박스 위치 오류 기록
3. Context·Audio 모듈과 고정 예시를 사용한 실제 안내 이벤트 통합 검증
4. 실제 정류장에서 낮·밤·거리·흔들림 조건으로 신뢰도 임계값과 프레임 간격 조정
5. 현장 실패 장면을 라벨링하고, 촬영 시퀀스 20%는 평가용으로 남긴 채 통합 모델 fine-tuning
6. 현장 평가를 통과한 클래스만 실제 음성 안내 후보에 추가

## 다른 개발자에게 전달할 내용

> 버스·버스 문·방치 전동 킥보드·기둥·나무 줄기를 함께 찾는 Android용 통합 TFLite
> 모델이 준비되어 있습니다. 카메라 프레임에서 버스의 방향·화면상 거리·접근 여부를
> `LEFT`, `NEAR`, `APPROACHING` 같은 안내 후보로 반환할 수도 있습니다.
>
> 앱에서는 `ANDROID_TFLITE_HANDOFF.md`에 따라 카메라 프레임을 640×640 RGB
> float32 형식으로 바꿔 TFLite 모델에 넣고, 결과를 화면 또는 안내 흐름에 연결하면
> 됩니다.
>
> Context·Audio 쪽에서는 AI가 보내는 방향·거리·접근 상태를 받아 실제 음성 문구,
> 공간음향, 중복 안내 방지 규칙을 적용하면 됩니다.
>
> 통합 모델은 29,885장으로 학습했으며, 학습에 쓰지 않은 내부 테스트에서 전체
> mAP50은 0.849였습니다. 다만 실제 정류장·보도·휴대폰 카메라 환경의 검증은 아직이므로,
> 실패 장면으로 통합 모델을 fine-tuning한 뒤 실제 안내 대상 포함 여부를 결정합니다.
