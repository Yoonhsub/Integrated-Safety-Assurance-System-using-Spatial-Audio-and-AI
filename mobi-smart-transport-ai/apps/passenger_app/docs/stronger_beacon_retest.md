# 다른 비콘이 더 강할 때 목표 비콘 유지 시험

기존 수신 증빙은 목표 A 위주여서 다른 비콘 B가 실제로 수신되고 더 강했는지 입증하지 못했다. 이번 변경은 새 Android 시연 화면에서 두 시험 ID에 한해 진단 로그를 추가한다. 스캐너·평활화·근접 판단·목표 선택·오디오 규칙은 변경하지 않는다.

- `MOBI_DOOR_BLE_RAW`: 기존 FlutterBlueBeaconScanner가 신선도 검증 후 ID resolver에 전달한 원본 RSSI·플러그인 관측 시각.
- `MOBI_DOOR_BLE_SIGNAL`: 같은 관측 시각의 평활 RSSI·근접 등급·선택된 목표·목표 입력 수용 여부. `target_accepted=false`는 B에 대해 정상이며 다른 ID의 수신이 목표 관측을 갱신하지 않았다는 의미이다.
- `MOBI_DOOR_STATE`: 실제 안내 상태. 원본과 평활 로그를 ID·captured_at으로 연결하고, A/B는 비슷한 시간 구간의 복수 샘플로 비교한다. 단일 순간 RSSI만 비교하지 않는다.

목표는 A 고정이다. B가 더 강하더라도 A의 신선한 근접 등급만 사용한다. A가 끊기면 B가 계속 수신돼도 접근 안내를 보류해야 한다. RSSI로 좌우 방향이나 탑승 허가를 만들지 않는다. 이 진단은 실제 버스 인증·서버 판정이 아니다.

## 실행 순서

1. 실제 이어폰 미디어 연결·두 비콘 전원 ON. 카메라 OFF, 위험 none·모의 전체 위험 해제 스냅샷 ON을 사용한다. BLE는 실측이고 위험 해제만 모의이다.
2. A는 휴대폰 가까이, B는 멀리 두고 스캔한다. A/B의 ID·원본/평활 RSSI·원본 시각을 수집한다.
3. A만 더 멀리 두고 B를 휴대폰 가까이 둔다. 목표 A 선택은 유지한다. 실제 거리 측정이 어렵다면 정량 거리로 기록하지 않는다. B가 더 강한 복수 샘플 구간을 확보한다.
4. A가 유효하면 안내가 A 등급과 일치하는지, B 강도 때문에 near로 바뀌지 않는지 확인한다.
5. A만 끄고 B는 가까이 켜둔다. B 연속 수신과 A의 마지막 관측 시각, unavailable 전환을 대조한다. A를 복구하면 새 목표 관측 후 재개되는지 확인한다.

이번 변경은 관측 로그만 추가했다. 기존 목표/중단/오디오 경로 관련 회귀 테스트 27개 통과, 정적 분석 문제 없음, Android debug APK 빌드 성공(24.9초). 이전 이어폰 보호 코드의 전체 580개 테스트 결과와 이번 제한된 회귀 결과를 구분한다.
