## 판정과 남은 작업

1. 장비 수신·모의 위험 경고·더 강한 시험 B의 비수용·일부 통합 중단 경로는 위 범위에서 통과했다. 실제 카메라 장애물 경고·목표 문까지의 연속 안내·전체 탑승 완료는 통과로 표시하지 않는다. B 간섭 통과도 실제 차량 인증을 뜻하지 않는다.
2. 지원 실물이나 실제 기록 영상으로 검출→좌우 경고를 확인하고, 최종 v2c APK에서 좌우·위험 선점·신호 상실을 같은 리허설로 반복한다. 실제 장면이 없으면 이벤트 모의 입력임을 표시한다.
3. B 후속 시험에서는 원본/평활값·등급·시각을 함께 수집했고, 마지막 A 관측→보류 상태는 로그 기준 약 3.006초였다. 아직 A의 approaching 구간 전환은 실측 확인하지 않았으며, 물리 전원 차단 시각·음향 지연은 별도 계측 대상이다. 근접 문구와 단절 관찰만으로 이동 추세·정확한 거리·문 방위를 확정하지 않는다.
4. 서버 수신 성공과 목표 버스 판정 성공은 별도이다. REAL_BLE의 기존 NO_BEACON/WAITING_FOR_BUS 문서 경로와 이 로컬 근접 안내를 혼동하지 않는다. 실제 차량 인증·자동 탑승 완료 기능은 추가하지 않았다.
5. 문 열림·발밑 단차/틈·승하차 동선 확인은 별도 미구현 항목이다. 가까움에서는 문·발밑 확인을 요청하고 수동으로 마친다.

## 자동 검증·정리

- 이어폰 보호 수정 코드: 전체 Flutter 테스트 580개 통과·기존 조건부 9개 건너뜀, 정적 분석 문제 없음. Android debug APK 40.1초·localhost 웹 빌드 41.2초 성공.
- 후속 관측 로그 추가 코드: 관련 회귀 테스트 27개 통과, 정적 분석 문제 없음, Android debug APK 24.9초 성공. 안내 판단 규칙은 바꾸지 않았다.
- 실행 결과를 받지 못한 항목은 미실행으로 남겼다. 로그의 출력 요청·cue 완료와 담당자의 실제 청취 관찰을 구분했다. 음향 파형·TTS 실제 라우팅 장치·무음 전환 지연은 계측하지 않았다.
- 초기 A 전원 차단 시험은 조작 시각·마지막 수신 시각을 함께 계측하지 않았다. 후속 B 시험에서는 마지막 A 관측→앱 보류 상태 약 3.006초를 로그로 대조했지만, 물리 전원 차단·실제 음향 지연의 측정은 아니다. 일부 중단 시험에서는 이전 문장이 이미 끝났으므로 진행 중 음성 선점의 증거로 확대하지 않았다.
- 마지막 수동 arrived 확인 후 21:29:18.356 ACTIVITY_PAUSE·activeTracks=0. 앱을 홈으로 보내 정리했고 Bluetooth는 켜둔 상태로 확인했다. 해당 작업의 두 로그 수집 프로세스는 종료했다. 기기·이어폰·비콘 전원은 담당자가 관리한다.
- 원본 로그는 로컬에 보존했다. 인계 묶음에는 관련 상태/cue/스캔 로그만 추출하여 VM debug 서비스 주소를 제외한 `door-camera-device-evidence.log`, `headphone-fix-device-evidence.log`를 사용한다.
