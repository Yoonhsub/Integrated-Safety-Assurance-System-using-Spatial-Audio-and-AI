# 탑승문 접근 안내 중단 조건 — 11월 15일 시연 준비

현재 단계는 **공통 중단 상태 모델 + 모의/기록 입력 웹 재생 화면 + 실측 BLE 기반 Android 음향 시연 화면**이다. Android 새 시연은 실제 스캐너를 한국어 TTS·좌우 스테레오 출력에 연결했다. 카메라 실측 탐지를 명시적인 시연 주의 규칙에 연결하는 선택 기능도 추가했다([카메라 시연](door_camera_demo.md)). 학습된 충돌 위험도·서버 판정·실제 머리 추적 통합은 미완료이다. 새 버전의 실기기 청취는 아직 미실행이다. 실제 탑승 가능 여부나 문 열림/발밑 안전을 판단하지 않는다.

## 동작

- 선택된 문 ID의 새 관측만 받는다. 다른 ID·중복·역순·미래·기한이 지난 관측은 유효 시각을 갱신하지 않는다.
- 목표 비콘 관측이 3초 이상 오래되면 접근 안내를 끊고 “탑승 위치를 다시 확인해 주세요”를 안내한다. 새 콜백이 없어도 100ms 주기 tick에서 검사한다.
- 위험 정보도 신선한 전체 스냅샷이 있어야 한다. 위험도 순으로 하나를 선택하고, 동률은 ID 순으로 결정한다. 방향 불명은 중앙 스테레오 경고로 전달한다. 현재는 주의도 보수적으로 접근 안내보다 우선한다.
- 위험 관측이 만료되는 것을 장애물이 사라졌다고 해석하지 않는다. 위험 스냅샷이 2초 이상 오래되거나 잘못된 입력이면 주변 정보 확인 상태에서 안내를 멈춘다.
- 명시적인 새 위험 해제 스냅샷을 받은 뒤에도 **그 해제 시점 이후의 목표 비콘 관측**을 받을 때까지 재개하지 않는다. 경고 도중 받았던 비콘 값만으로 재개하지 않는다.
- 기존 `SpatialVerificationEngine`/`SpeechPriorityCoordinator`/웹 스테레오 출력으로 정지 확인 후 다음 cue/음성을 시작한다. 이전 비동기 재생 준비가 늦게 끝나도 당시 요청의 유효성을 다시 검사한다.
- STOP, 화면 비활성화, 출력 정지 확인 실패에서 새 안내를 차단한다. 출력 실패 후에는 페이지를 다시 열어야 한다. 화면 복귀로 입력 모의 재생이나 안내를 자동 시작하지 않는다.
- 가까움에서는 “탑승 위치 근처입니다. 문과 발밑을 확인해 주세요”까지 안내한다. 도착 상태는 신선한 가까움 상태에서 시연자가 확인 버튼을 눌렀을 때만 바뀐다.

3초/2초는 현재 시험 기본값이며 실측으로 보정한 현장 수치가 아니다. 모든 모델 시각은 같은 세션의 단조 증가 경과 시간이다. 실제 수집기를 연결할 때 wall-clock/서버 수신 시각을 그대로 섞거나 관측 시각을 tick마다 새로 만들면 안 된다.

## 실행

Flutter가 PATH에 있는 PowerShell에서 프로젝트 루트(`mobi-smart-transport-ai`)를 기준으로 실행한다. 출력 경로는 저장소 밖의 아직 없는 폴더를 지정한다.

```powershell
./scripts/build_local_spatial_verification.ps1 -DoorApproach -OutputPath C:/mobi-door-demo
python -m http.server 5280 --bind 127.0.0.1 --directory C:/mobi-door-demo
```

PC 브라우저에서 `http://127.0.0.1:5280`을 직접 연다. `-DoorApproach`와 `-GuidanceRuntime`은 함께 사용할 수 없다. `MOBI_LOCAL_DOOR_APPROACH=true`를 명시한 localhost debug 진입점만 허용한다. 이 진입점은 Android Gradle 진입점 허용 목록에 추가하지 않았다. 빌드 스크립트는 기존 웹 오디오 graph와 로컬 한글 폰트를 재사용한다. 자동 재생은 없다.

## 모의 리허설

1. “새 장애물 전체 스냅샷 모의 재생”과 “새 목표 비콘 관측 모의 재생”을 켜고 안내를 시작한다. 위험도 none에서 접근 상태를 확인한다.
2. 위험도를 danger로 바꾸고 방향을 좌/우/불명으로 바꿔 경고와 접근 음성 중단을 확인한다. 불명 방향은 중앙이다.
3. 경고 중 목표 관측 재생을 끈 뒤 위험도를 none으로 바꾼다. 새 목표 관측을 기다리는 상태로 남는지 확인한다. 목표 관측 재생을 켜 새 관측이 들어온 뒤에만 재개해야 한다.
4. 접근 중 목표 관측 재생을 끈다. 3초 후 안내 중단과 탑승 위치 재확인 문장을 확인한다. 위험 스냅샷 재생을 끄면 2초 후 주변 정보 재확인 상태가 된다.
5. 목표 관측을 복구하고 가까움 구간을 켠다. 문과 발밑 확인 요청을 확인한 뒤 “시연자 도착 확인”을 누른다. 가까움만으로 도착 상태가 되면 안 된다.

## BLE 입력과 탐지 기록 재생 연결 (2026-11-11)

- `door_input_adapter.dart`: 기존 스캐너의 평활화된 `BeaconSignal`과 기존 근접 등급을 재사용한다. `CLOSE/VERY_CLOSE`는 가까움, `MEDIUM/FAR`는 접근 상태이며 실제 이동 방향이나 거리 변화의 인증이 아니다. RSSI로 좌우를 만들지 않는다.
- 원본 관측 시각의 나이를 세션 단조 시각으로 한 번 변환한다. 3초 이상 오래된 값, 미래 시각, 세션보다 오래된 값, 중복/역순 시각은 거부한다. UI 갱신으로 수신 시각을 늘리지 않는다.
- 실기기 연동확인 화면의 **탑승문 중단 조건 · 상태 확인 전용**은 실제 스캔 콜백을 사용한다. 목표 A/B 변경 시 상태를 새로 만들고 중지한다. 스캔 종료/오류와 화면 이탈 시 중지한다. 위험 정보는 아직 실시간 연결되지 않았으므로 기본은 안내 보류이다.
- 이 상태 패널은 **오디오를 제어하지 않는다**. 아래 기존 WT901 시험음은 별도 기능이다. 새 중단 조건이 기존 시험음을 중단한다고 해석하지 않는다. Android 통합 음향은 후속 작업이다.
- AI 비전의 `vision_codec.dart` 출력에는 `classId/confidence/bbox`가 있고 위험도는 없다. 웹 리플레이 패널은 이 계약의 JSON 한 스냅샷을 읽어 화면 좌우를 사용한다. 위험도는 운영자가 선택한 **모의 값**이며 검출 신뢰도나 박스 크기를 위험도로 바꾸지 않는다. 탐지 대상이 있을 때 모의 위험도 `none`으로 안전 판정을 만들 수 없다.
- 정상 빈 전체 스냅샷만 해제로 처리한다. 잘못된 JSON, unavailable 응답, 잘못된 좌표는 거부하고 안내를 중지한다. 방향 누락은 중앙 경고이다. 하나의 프레임을 다시 클릭하면 명시적 새 재생이며, 실시간 카메라로 표시하지 않는다. 원본 `capturedAt/source/frameId`는 화면에 보존한다. 자동 반복은 없고 2초 뒤 위험 정보가 만료된다.

## 새 입력의 실행 순서

웹 빌드/실행은 아래 기존 localhost 절차와 같다. **AI 탐지 JSON 한 프레임 재생**을 펼치고 모의 위험도 `danger`를 선택한 뒤 다음 단일 응답을 붙여넣고 **탐지 스냅샷 1회 재생**을 누른다. 먼저 **안내 시작**을 눌러 브라우저 오디오를 준비한다. 왼쪽 경고 요청, 2초 뒤 정보 만료에 따른 안내 중단을 확인한다. 실제 청취는 별도로 기록한다.

```json
{"schemaVersion":"1.0.0","source":"mock","status":"ok","frameId":"rehearsal-left-1","capturedAt":"2026-11-11T00:00:00Z","detections":[{"classId":"pole","confidence":0.9,"bbox":{"x":0.1,"y":0.1,"w":0.1,"h":0.5}}]}
```

휴대폰에서는 기존 **실기기 연동확인 → 권한 허용 → 버스 탐색 시작** 후 **중단 상태 확인 시작**을 누른다. **모의 위험 해제 1회 (2초)** 뒤 새 목표 광고가 들어와야 근접 상태를 표시한다. 2초 후에는 위험 정보가 만료되므로 다시 보류하는 것이 기대 동작이다. 이 버튼을 연속 재생하는 실제 위험 감지기로 해석하지 않는다. 다른 비콘만 수신돼도 목표 신호는 갱신되지 않는다. 기존 소리는 먼저 수동으로 중지하고 상태 패널만 검사한다.

## Android 실측 BLE → 안내음 중단 연결

`native_door_approach_page.dart`는 Android debug 전용이다. 로그인 없이도 시작 화면의 **이어폰·BLE 기기 점검 → 탑승문 접근·중단 시연 (실측 BLE)**으로 열 수 있다. 모드 선택 화면에도 같은 진입 버튼이 있다. 기존 상태 확인 전용 패널이나 WT901 시험음과 별도이며, 동시에 실행하지 않는다.

- 실제 `FlutterBlueBeaconScanner`의 평활 RSSI·근접 등급을 재사용한다. 목표는 시연용 A `C3:00:00:5C:B9:47`로 고정되어 있다. 실제 버스 인증 매핑이 아니다. 원본 관측 시각·평활 RSSI·등급은 화면에 표시한다. 원본 RSSI 상세는 기존 실기기 진단을 사용한다.
- `NativeDirectionalCueOutput`과 `FlutterSpeechEngine`을 재사용한다. 장애물 위험 시 접근 음성을 중지하고 정지 확인 뒤 방향 cue와 경고 음성을 출력한다. 신호 상실은 접근 음성을 중지하고 재확인 문구를 출력한다. RSSI에서 방향을 만들지 않는다. 새 화면은 센서 연결을 요구하지 않으며 HRTF·머리 추적을 사용하지 않는다.
- 스캔 오류·종료, Bluetooth 꺼짐/권한 상태 오류, STOP, 화면 이탈은 안내를 중지한다. 재연결만으로 소리가 재개되지 않는다. 사용자가 다시 스캔·안내를 시작해야 한다. 늦게 끝난 권한·오디오 준비 요청도 STOP 이후 새 작업을 시작할 수 없다.
- 위험 해제 뒤 새 목표 관측이 있어야 재개한다. 다른 비콘·중복 콜백·오래된 값은 목표 시각을 갱신하지 않는다. 출력 정지가 확인되지 않으면 오류를 고정하고 새 안내를 막는다.
- 상태 전환 로그는 `MOBI_DOOR_STATE at_us=... target=... phase=... risk=MOCK_OR_REPLAY`이다. 이 로그는 출력 요청 상태의 증거이고 실제 청취 성공 증거는 아니다.

### 담당자 실기기 재시험

1. 이어폰을 미디어 출력으로 연결하고 음량을 낮춘다. 다른 진단의 소리를 중지한 뒤 새 화면을 연다.
2. A·B 전원을 켜고 **실측 BLE 스캔 시작 (5분)**을 누른다. 권한을 허용하고 A의 식별자·시각·RSSI·등급이 갱신되는지 기록한다.
3. **새 장애물 전체 스냅샷 모의 재생**을 켠다. 모의 위험 `none`은 이번 리허설에서만 명시적으로 제공하는 위험 해제 입력이다. 실제 AI가 안전을 확인했다는 뜻이 아니다. **안내 시작**을 누르고 새 A 관측 후 접근/근접 안내를 듣는다.
4. 모의 위험을 `danger`로 바꾸고 왼쪽 또는 오른쪽을 선택한다. 기존 안내가 끊기고 방향 경고가 들리는지 기록한다. 위험을 `none`으로 돌린 뒤 새 A 관측 이후 재개되는지 확인한다.
5. A 전원을 끈다. B가 계속 수신돼도 약 3초 뒤 접근 안내가 멈추고 재확인 안내가 나와야 한다. A를 복구하면 새 수신 후 재개할 수 있다. 실제 시각·들린 문장을 기록한다.
6. STOP, 홈 이동, Bluetooth 끄기를 각각 시험한다. 소리가 멈추고 연결 복구만으로 자동 재생되지 않는지 확인한다. 자동 재생·스피커 우회 여부는 관찰 결과로 남긴다. 도착은 가까움 상태에서 시연자가 직접 확인한다.
